How this was built

A retrieval system is easy to demo and hard to trust. What follows is what was measured, what broke once real traffic hit it, and what was left undone on purpose.

01 Measuring retrieval

Every claim on the front page comes from a run you can reproduce: 56 questions with known answers, over 27 documents, replayed through the live pipeline. The result ships with the app rather than being re-run by each visitor.

The metric was wrong for months

Retrieval is scored by checking whether a retrieved passage contains the known answer. That check used a similarity threshold of 0.6 — and at 0.6 it scored 79.6% of true containments as misses. The cause was length, not language: a one-line passage against a 500-token chunk scores low even when the sentence sits verbatim inside it. Most of this project's historically poor retrieval numbers were a broken ruler.

Two metrics, because one flatters

The similarity-based score has a direction to its error: false positives rise with corpus size, from 17.2% at 21 passages to 19.5% at 39. Adding filler documents makes the score go up. So the build gate reads a second, deterministic set — plain string containment, no threshold, no embedding — which moves only when retrieval actually changes.

The corpus argues back

The 27 documents are deliberately confusable: the same firm, the same vocabulary, numbers of the same shape about different things — S$26,000 per commercial case beside S$9,800 per residential one. Expanding it made the scores fall, which was the point. A corpus where every document is about something different tests nothing.

A grader that fails open

A judge that times out is a broken grader, not a failed answer. It reports ungraded, never failed — rendering the second would be a confident false claim about your documents. The published run shows 8 ungraded questions on its face rather than quietly dropping them and reporting a better average.

02 What only production taught

Each of these passed every test and still failed in front of a real visitor. The measurements are from the deployed app.

Sign-in · 8.4s → 0.95s

Signing in did three things: created the workspace, copied sample documents into it, and cleaned up after previous visitors. Only the first was asked for. The rest now happens while you read the page.

Schema checks · 18 round trips

The database schema was verified before every store operation — six network round trips, eight call sites. Its own comment said "once". It wasn't. Now it is.

Connection checks · one per request

A liveness ping before every connection checkout costs nothing against a local file and a full round trip against a hosted database. Replaced by recycling connections on age.

Identity · 1.2s → 30ms

The session cookie is HTTP-only, correctly — so the page could not read it and left the corner blank until the server answered. A second cookie carries only "guest" or "account", enough to paint the right control immediately.

The benchmark crashed

A refactor renamed a variable and left one reference behind, on a line only the full run reaches. Every full benchmark had been dying at that line — found by running it, not by the 211 tests.

A feature that made answers worse

Deep search sent the model passages the ranked search had already supplied. One question went from a correct answer to "I couldn't find this" with the feature on. Duplicates are now dropped before the model sees them.

03 Shaped by one constraint

The app is a single serverless function, frozen the instant it sends a response, with sixty seconds to work in. Nearly every structural decision follows from that.

No background work

A thread started during a request is killed when the response is sent. Long jobs are sliced instead: each request does one bounded piece and commits it, so progress survives being frozen.

Nothing periodic runs inside

Guest workspaces expire after 30 minutes, which needs a clock the function does not have. A scheduled job outside calls in every 15 minutes behind a shared secret.

Nothing writable on disk

The project directory is read-only and any local file vanishes between requests. Every durable byte goes to Postgres — including the document text that word-for-word search reads.

04 Deliberately unfinished

Cold starts

The first visitor after an idle period waits 25–30 seconds. Importing the application accounts for 1.25s of that; the rest is the function starting and the database waking. No amount of application code fixes it — it is a hosting plan decision, so the top bar is built to stay honest while it happens rather than pretending otherwise.

Word-for-word search does nothing here

On the sample workspace it is a no-op, and correctly so: with six passages, ordinary search already returns all of them, and there is nothing for an exhaustive scan to rescue. It earns its place on real document sets, which is where it was left.

Tools the model chooses between

The pipeline is fixed today and word-for-word search is a switch you set. The intent is that the model decides per question — was retrieval enough, does this need a literal scan, does it need something outside. The shape is already there: that search is passed as a function, not a flag, so a second and third tool have the same signature.
