How this was built

A search system is easy to demo and hard to trust. Here is what was measured, what broke in front of real people, and what was left undone on purpose.

01 The pipeline

A question does not go straight to a language model. It passes through five stages, and each one is shaped by a constraint of running this on one serverless function. This used to open the landing page — it belongs here, with the rest of the reasoning.

Input Index chunked + embedded
Stage 01 Rewrite sharpen the query
Stage 02 Retrieve vector + BM25
Stage 03 Rerank cross-encoder rescore
Stage 04 Generate answer + citations
Stage 05 Judge grade the answer
Embeddings

One fixed vector(768) column shared by every model, so models swap without a migration. The config fingerprint changes with them and invalidates stale chunks.

Model output

Reasoning models emit a thinking trace. It is stripped before the rewrite is used — otherwise 1,400 characters of deliberation become the search query.

Storage

Neon Postgres with pgvector is both the application database and the vector store. Chroma swaps in for local development behind a single dispatch module.

Configuration

How wide the net is cast is re-read from the database on every request, so tuning it takes effect on the next question with no redeploy.

Runtime

One FastAPI serverless function. The repo directory is read-only and the process freezes the instant a response is sent, so every writable byte goes to the database.

Fail open

A judge that times out is a broken grader, not a bad answer. It reports ungraded — never failed, which would be a confident false claim about your documents.

02 Measuring retrieval

56 questions with known answers, replayed through the live pipeline. The hard part was trusting the scoreboard.

The ruler was broken

The check for "did we find the right passage?" was calling four in five correct answers wrong. Most of the early bad scores were the measurement, not the search.

One score flatters

The similarity score creeps upward as the corpus grows — add filler and it improves. So the build gate uses a second score that can't be gamed that way.

The corpus argues back

27 documents about the same firm, in the same words, with different facts. Expanding it made the scores fall. That was the point.

"Don't know" beats a guess

When the grader itself fails, the answer is marked ungraded — never failed. Eight questions show that on the published run rather than being quietly dropped.

03 What only production taught

Every one of these passed the tests and still failed in front of a real visitor. Numbers are from the live app.

The server was an ocean away

Every trip to the database took 420ms — on a table with 240 rows. Not a slow query: the code ran in Virginia and the data lived in Singapore. Moving them together made it 3ms.

Sign-in · 8.4s → 0.05s

It was building the workspace, copying sample files and tidying up after old visitors. Only the first was asked for.

Setup checks · 18 → 0 per sign-in

The database layout was re-verified before every single operation. The comment above it claimed it happened once.

Deleting a file · 2.7s → 0.08s

Three round trips, and two rounds of clever fixes that changed nothing — because the distance was the cost, not the work.

Waiting to be marked · 56% of the wait

Every answer was scored before you were allowed to read it — and scoring cost more than writing it. The answer now arrives first and the marks land a moment later.

It invented a product

Ask two questions, then a third about something else, and the app said the answer wasn't in your documents — a paragraph from one it had already given you. The step that tidies your question had glued the previous subject onto it.

Sign-in button · 1.2s → 30ms

The page couldn't read its own login cookie, so the corner sat empty until the server replied. A second, harmless cookie fixed it.

The benchmark never ran

A rename left one stale reference on a line only the full run reaches. Every full run had been dying there. 211 tests missed it; running it found it.

A feature that hurt

Deep search handed the model text the ranked search had already given it. One question went from right to "I couldn't find this".

The door was unlocked

One address, no password, and you were signed in — to an account holding real documents. Nothing pointed at it any more, which is exactly why nobody had looked at it.

A perfect, empty workspace

After a search-engine change, returning visitors saw their files listed and ready while every question came back empty. It looked right and was hollow underneath. Fresh visitors were fine, which is why testing missed it.

The ruler, again

A new search engine scored 0.31 where the old one scored 0.90 — and was fine. It was being measured with the old one's yardstick. Same mistake as the first card, a year of lessons apart.

04 Shaped by one constraint

One function, frozen the instant it answers, with sixty seconds to work in. Almost every decision above follows from that.

No background work

A background thread dies the moment the answer is sent. Long jobs are sliced: each request does one piece and saves it.

Nothing periodic runs inside

Guest workspaces expire after 30 minutes — but the app has no clock. Something outside calls in every 15 minutes.

Nothing writable on disk

Files written during a request are gone by the next one. Every byte that must survive goes to the database.

05 When it comes up short

Searching your documents can fail two ways: nothing close enough comes back, or the model reads what did and says the answer isn't there. Both used to end the same way — a shrug. Now they are where the app starts working.

It reads everything, word for word

Ordinary search ranks, and whatever falls below the cut may as well not exist. So when ranking comes up short the app reads every document you own, literally, looking for your exact words. It costs no AI call at all — and nothing on a question that was already answered.

A model picks the tool

"This should be in their documents, the search just missed it" and "this could never have been in a private file" need different answers, and no rule can tell them apart. A second, faster model decides — in about 0.7 seconds, and it got all twelve test cases right. It can improve the choice; it can never block one.

The web stays switched off

The promise is answers from your documents. An app that quietly searched the web whenever yours fell short would be grounded only most of the time. So it is off until you turn it on — and then it is the last resort, after both searches, with everything it finds labelled as coming from outside.

06 Deliberately unfinished

Cold starts

The first visitor after a quiet spell waits about 9 seconds while the server and database wake up. It was 25–30, blamed on the hosting plan — wrongly. Most of it was the same ocean as everything else on this page.

Word-for-word search does nothing here

With six sample passages, ordinary search already returns all of them — there is nothing left to rescue. It earns its place on real document sets, which is an honest limit rather than a bug to chase.

It chooses, but only once

A model now picks which tool to reach for, and picks well. What it cannot do is look at what came back and change its mind — and a server that freezes the moment it answers cannot hold an open-ended loop to let it.
